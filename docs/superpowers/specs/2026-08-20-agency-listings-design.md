# База объектов агентства на urpak.kg

Дата: 2026-08-20

## Зачем

urpak.kg больше не развивается как собственный продукт. Площадку арендует агентство
недвижимости. Им нужна база объектов, которую агенты показывают клиентам с компьютера
и по которой сами подбирают варианты под запрос клиента. Референс интерфейса — их
текущая CRM: набор фильтров над сеткой карточек, вкладки-секции и разделы
Варианты / Аренда / Удалённые / Счета.

Стили остаются наши (текущая тема urpak.kg, светлая и тёмная). Со скриншотов берём
только состав фильтров, секций и карточки.

## Решения

| Вопрос | Решение |
|---|---|
| Судьба старого наполнения | Полное перепрофилирование. Главная = база объектов. Новостройки/Застройщики убираем из меню, код и API оставляем нетронутыми |
| Доступ | Просмотр публичный (чтобы показывать клиентам), агентские действия — под логином |
| Разделы | Варианты, Аренда, Удалённые, Счета — все четыре |
| Ввод объектов | Формы на сайте, с загрузкой фото |
| Счета | Комиссии по сделкам |
| Справочники | Таблицы в БД + сидинг типовыми бишкекскими значениями, правятся в админке |
| Скрыто от публики | Телефон собственника, точный адрес, внутренние заметки |
| Навигация | Существующий верхний хедер, меняем только пункты меню |

## Архитектура

Новое Django-приложение `agency` рядом с существующим `backend`. Существующие модели
Developer / Project / Apartment и их API не трогаем — они просто перестают быть видны
в меню фронта.

Отвергнутые альтернативы:

- **Расширять `Apartment`.** Модель жёстко привязана к `Project → Developer` и к
  модерации `is_approved`; вторичке и аренде ни то, ни другое не нужно. Модель стала бы
  свалкой из полей двух несвязанных доменов.
- **CRM на Django-шаблонах.** Второй UI-стек рядом с Next.js; текущие стили пришлось бы
  дублировать руками и поддерживать в двух местах.

### Модели (`agency/models.py`)

**Справочники.** Общая база `DictionaryModel` (abstract): `name`, `position`,
`is_active`. Наследники: `PropertyType`, `District`, `Series`, `Complex`, `Condition`,
`ListingStatus`. Заполняются data-миграцией, дальше правятся в админке.

**`Agent`** — `OneToOneField(User)`, `full_name`, `phone`, `is_active`. Он же «Куратор».

**`Listing`** — единая сущность для продажи и аренды:

- `deal_type`: `sale` | `rent`
- FK: `property_type`, `district`, `complex`, `series`, `condition`, `status`, `curator`
- `rooms`, `floor`, `total_floors`, `area_m2`, `price`, `currency` (`USD` | `KGS`)
- Публичное: `description`, `landmark` (ориентир), фото
- Агентское: `owner_phone`, `address`, `internal_note`
- Метки-секции: `is_urgent`, `is_exclusive`, `is_alternative`, `is_barter`
- `created_at`, `updated_at`, `deleted_at`, `deleted_by`

Мягкое удаление: `deleted_at IS NOT NULL` — объект уходит в раздел «Удалённые» и
исчезает из основной выдачи. Физического удаления в API нет.

**`ListingImage`** — `listing`, `image` (S3, как у проектов), `position`.

**`Deal`** — счета по комиссиям: `listing`, `client_name`, `deal_date`, `amount`,
`commission`, `currency`, `curator`, `is_paid`, `note`, `created_at`.

### API `/api/agency/`

| Метод | Путь | Доступ |
|---|---|---|
| GET | `/listings/` | все |
| POST | `/listings/` | агент |
| GET | `/listings/{id}/` | все |
| PATCH | `/listings/{id}/` | агент |
| DELETE | `/listings/{id}/` | агент, мягкое удаление |
| POST | `/listings/{id}/restore/` | агент |
| GET | `/listings/deleted/` | агент |
| GET/POST | `/deals/` | агент |
| PATCH/DELETE | `/deals/{id}/` | агент |
| GET | `/dictionaries/` | все |
| POST | `/auth/login/`, `/auth/refresh/` | все |
| GET | `/auth/me/` | агент |

Аутентификация — `djangorestframework-simplejwt` (добавляется в requirements).

Параметры фильтрации `/listings/`:

```
id, q, deal_type, property_type, complex, series, district, condition,
status, curator, rooms, floor, price_min, price_max, area_min, area_max,
tab=all|mine|alternative|exclusive|barter, ordering, page
```

`q` ищет по описанию, ориентиру и названию ЖК. По адресу — только для
аутентифицированных, чтобы адрес нельзя было подобрать перебором через поиск.

`tab=mine` требует логина и фильтрует по `curator = текущий агент`.

`/dictionaries/` отдаёт одним ответом все справочники и список активных агентов —
фронту нужен один запрос на заполнение всех селектов.

Сериализатор `ListingSerializer` убирает `owner_phone`, `address` и `internal_note`
из ответа, если пользователь не аутентифицирован.

### Фронт (репозиторий `urpak-frontend`)

Страницы:

- `/` — Варианты (продажа): фильтры + вкладки + сетка карточек
- `/rent` — Аренда
- `/trash` — Удалённые (агентам)
- `/invoices` — Счета (агентам)
- `/listings/new`, `/listings/[id]/edit` — формы, с загрузкой фото
- `/listings/[id]` — карточка объекта, её показывают клиенту
- `/login`

Компоненты: `FiltersBar` (состав полей задаётся пропсом), `Tabs`, `ListingCard`,
`AuthProvider` (JWT в localStorage, refresh при 401).

Фильтры по разделам:

- Варианты: id, ключевые слова, тип объекта, ЖК, этаж, состояние, комната, статус,
  районы, цена от, цена до, м² с, м² по, куратор
- Аренда: id, тип объекта, этаж, состояние, комната, статус, районы, цена от,
  цена до, куратор

Вкладки:

- Варианты: Все варианты, Мои варианты, Альтернатива, Эксклюзив, Бартер
- Аренда: Все варианты, Мои варианты

Карточка: фото, бейдж «Срочно» при `is_urgent`, заголовок
«Квартира, 104 серия, Южный / 4-ком, 3-этаж», `ID:{id}`, дата создания, кнопки
поделиться / редактировать / удалить (последние две — агентам).

Состояние фильтров синхронизируется с querystring: агент может скинуть клиенту ссылку
на готовую подборку. «Поделиться» копирует ссылку на объект.

Хедер: пункты меню становятся Варианты / Аренда / Удалённые / Счета / Вход. Страницы
`/projects` и `/developers` остаются в кодовой базе, но из меню исчезают.

Стили — существующие классы `.card`, `.btn-primary`, `.btn-secondary`, `.input`,
`.select` и текущая цветовая тема. Никаких новых цветов: кнопка «Обновить» будет
оранжевой (наш primary), а не красной как в референсной CRM.

## Обработка ошибок

- Недоступный API — на списках показываем сообщение с кнопкой «Попробовать снова»
  (как на текущей странице проектов).
- 401 на агентском действии — редирект на `/login` с возвратом на исходный адрес.
- Валидация форм — ошибки от DRF раскладываются по полям.
- Пустая выдача — «Ничего не найдено» и кнопка сброса фильтров.

## Тесты

Django-тесты в `agency/tests/`:

- скрытие `owner_phone` / `address` / `internal_note` для анонима и их наличие для агента
- фильтрация по каждому параметру и по диапазонам цены и площади
- `tab=mine` требует логина и отдаёт только объекты текущего агента
- вкладки `exclusive` / `alternative` / `barter`
- DELETE помечает `deleted_at`, объект пропадает из списка и появляется в `/deleted/`,
  `restore` возвращает
- анонимный POST/PATCH/DELETE получает 401

## План реализации

1. Приложение `agency`: модели, миграции, data-миграция со справочниками.
2. Админка для всех моделей.
3. Сериализаторы с сокрытием агентских полей; фильтр-класс; вьюсеты; урлы.
4. simplejwt, `MultiPartParser`, регистрация приложения в settings.
5. Тесты бэкенда.
6. Фронт: API-клиент, `AuthProvider`, `FiltersBar`, `Tabs`, `ListingCard`.
7. Фронт: страницы Варианты, Аренда, Удалённые, Счета, формы, деталка, логин.
8. Хедер и метаданные сайта.
9. Прогон: `manage.py check`, тесты, `next build`.

## Вне объёма

- Мобильное приложение и адаптив сверх того, что даёт текущая сетка.
- Импорт объектов из внешних источников и парсеры.
- Автоматическая выгрузка на доски объявлений.
- Роли и права тоньше, чем «аноним / агент» (например, руководитель против рядового).
